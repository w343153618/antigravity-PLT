# 多门店排列三登记系统规划

更新于2026-10-11。目标是帮助实体彩票店把顾客的真实购买、出票凭据、奖金核对与日结记清楚，让老板查看授权门店的汇总。首个版本建议从店员内部使用的手机网页开始，先在一家店证明账目准确、操作省时，再扩展多店。本文是开发方案，不代表系统已经实现或商业模式已获许可。

## 已知需求与待验证假设

|内容|当前状态|对设计的影响|
|---|---|---|
|大哥管理多家店，店长对应实体店|用户描述|组织、门店、员工和任职关系必须分开|
|顾客在线下店内购票，购票款交给店方|用户描述|系统记录线下事实；ERP记录不等于官方出票成功|
|可能全国覆盖|用户已确认|省市、兑奖提示、门店协议和权限分别维护|
|首批测试地区为江苏南京|用户本轮确认|先采用[南京模拟测试设定](NANJING-PILOT.md)，再替换成真实门店|
|每日可能三套方案|用户设想|可容纳多个方案及版本，不把“三套”写死成三个数据库字段|
|按奖金收20%，店长与平台各10%|用户已确认的商业设想|详见[商业与金额规则](BUSINESS-RULES.md)，尚不能直接启用收费|
|方案胜率高，亏损会更少|待验证，不能作为产品承诺|先保存完整成本和结果，避免只展示中奖案例|
|体彩销售费用为7%|用户提供的估计|须核实各店代销合同，不作为全国统一常量|
|模拟门店数与日登记量|用户授权生成：3店、90顾客、每店每日12—20笔|7天345笔模拟记录可直接用于设计；真实规模、预算和工期仍待确定|

## 先建立能够独立成立的产品价值

让店长少漏记、少重复登记、能找到票、能核清账，是可以现场验证的价值。统计和客户服务的便利应当在没有预测优势的情况下仍然成立。请用连续7个营业日的样本观察登记耗时、错误数和关账耗时，再决定是否值得铺开。

“中奖抽成”与免费内部登记是不同的业务条件。普通记录功能不依赖方案收费；即使收费方案最终不能开展，也应保留清晰账本。若后续讨论软件订阅或固定服务费，那是备选商业方向，不能把它记成用户已接受的方案。

## 角色及数据范围

|角色|需要做什么|允许看到什么|
|---|---|---|
|平台运维|配置、故障处理、备份|默认不浏览客户明细，必要支持须临时授权并留痕|
|经营主体负责人／老板|管理授权门店、人员、汇总|本组织授权门店；不是全国所有门店客户|
|区域负责人（后续）|管理分配门店|指定区域或门店集合|
|店长|本店登记、复核、日结、交班|本店客户与票据；调店后不能自动带走原店客户|
|店员|录入、查看职责所需记录|本店限定权限；重大更正交店长复核|
|财务／复核人|核账、确认线下收付、处理更正|授权账目；不需要方案编辑权限|
|顾客|首版无需账户|店内获得自己的登记或对账信息；客户在线操作属于后续另审范围|

员工是一个独立账号，任职记录含门店、角色、生效及失效时间。即使首版一人一店，也要支持换店和交班；历史记录保留当时的门店和经办人。全国不同经营主体分别隔离，不能因使用同一平台就互看顾客资料。

## 一天的业务流程

1. **顾客到店、官方渠道完成购买。** 收款和出票由有相应资格的店方完成，系统不连接投注终端下单。
2. **员工登记购买事实。** 选本店、客户或匿名散客、游戏、期号、票据，再录入实际玩法、号码、注数、倍数、金额。系统验算金额；票据有差异就放入待核对。
3. **关联方案（后续，经审查后）。** 只关联事前已确定的版本与适用明细；“方案存在”不表示客户真实买了。自选部分不自动计入服务费。
4. **核实官方开奖。** 首版人工录入官方来源并由另一个有权限的人复核；每次记录来源、期号、开奖号码、版本与复核时间。不确定时显示待核实。
5. **逐明细核奖。** 产生理论奖金清单，标明计算规则版本。这还不是实际兑奖到账。
6. **登记实际兑奖。** 店方根据真实凭据记金额、日期、税款和经办人；保留未兑、部分处理或争议状态。
7. **日结与交班。** 汇总实际购买、付款记录、理论奖金、实际兑奖、差异与待办；店长确认后锁定。次日更正走有原因的冲正记录，不覆盖旧账。

业务日期、录入时间、出票时间、期号、开奖日期、兑奖日期分别保存。跨日补录归属真实业务日期，并标出补录；不把补录时间伪装成开奖前已登记的证据。

## 首版功能范围

|页面／模块|必须解决的问题|验收重点|
|---|---|---|
|今日工作台|本店待核对、未核奖、未兑记录、日结差异|任务状态明确，不用“高收益”宣传占据首页|
|客户簿|顾客别名、店内编号、可选联系方式、记录查询|支持散客；不强制收身份证、通讯录或定位|
|购票登记|按真实票面录入与验算|前三种基本玩法先做到可靠；不支持的票型明确待人工核验|
|票据详情|一张票的多行、多倍、附件、经办记录|支持前导0；理论金额与原票一致|
|核奖与兑奖|官方开奖、理论奖金、实际到账分开|同一记录不能重复结算；纠错可追溯|
|日结与报表|店、日、期号、客户的金额与注数统计|总账能钻取明细；售票款不等于门店利润|
|门店与成员|建立门店、邀请员工、调整权限|跨店越权被服务端拒绝，员工离职权限及时回收|
|导出与操作记录|对账、留档、查错|按权限导出，必要字段脱敏，保留谁做了什么|

“数量”至少有三个指标：实体票张数、单倍基本注数、含倍数投注注次。例如一张含4注、3倍的彩票，是1张、4注、12注次、24元。UI不只写模糊的“数量”。

首版不包含顾客远程下单、充值钱包、自动代购出票、自动追号、奖金自动扣款、自动分账、真实方案预测引擎、员工工资和完整进销存。这些不属于当前最小登记闭环；以后按真实需求及业务许可分别决定。

## 数据关系

```text
经营主体 → 门店 → 客户记录 → 购买记录 → 实体票据 → 投注明细
                 ↑                         ↓
员工账号 → 有时效的门店任职             核奖结果 → 兑奖记录
                            游戏期号 → 开奖版本
方案 → 不可变方案版本 → 适用明细关联（后续）
收费政策版本 → 费用明细 → 收付确认／冲正（后续）
所有关键操作 → 操作记录；每日汇总 → 日结版本
```

|对象|最低必要信息|关键约束|
|---|---|---|
|经营主体与门店|主体编号、门店编号、省市、授权资料引用、状态|系统授权不替代官方代销资格|
|员工任职|账号、门店、角色、生效时间、结束时间|历史不随当前店长变动而重写|
|客户|所属主体/店、店内编号、别名、必要联系方式与告知记录|手机号不是跨店唯一身份依据，不擅自全国合并|
|购买记录|客户、门店、业务日、录入时间、实际付款记录|一笔购买可以多张票，暂不支持多人合买一张票|
|实体票|门店、票据标识、出票时间、期号、票面金额、附件引用|附件私有；条码和兑奖信息不作为公开分享图片|
|投注明细|玩法、原始选法、标准化基本注、倍数、规则版本|号码用定长字符串；不同购买的同号投注不能错误去重|
|开奖版本|游戏、期号、开奖号码、来源、复核人、状态|未核实不得记为已结算，更正不能覆盖原版本|
|核奖/兑奖|理论奖金、实兑金额、已核实税款、凭据、时间|可追溯到实际票与开奖版本；核奖与兑付分开|
|方案版本（后续）|编号、期号、版本、明细、形成时间、状态|方案发布后不可回改；原版本保留|
|收费政策（后续）|费基、比例、归属、舍入、有效期、协议版本|旧记录使用原政策；费用与实收分别记录|

先支持三种基本玩法的单式；复式等复杂票型只有在展开结果与真实终端样票一致后才开放自动计算。所有自动判奖都应使用已展开的基本注与倍数，而不是直接拿“包号”“稳健方案”等名称计算。

## 金额与防错原则

- 金额用整数“分”或精确十进制保存；比例用精确值；一次确定舍入规则及差额归属。
- 将官方奖金规则、当地终端方式、方案内容、商业收费政策分别版本化；不能用一个“返奖比例”字段代替。
- 票据登记、批量导入、核奖和后续收费都有防重复标识。网络重试不得多记一笔；客户确实另买的一张同号票则应正常计入。
- 已确认票据、开奖、结算发生更正时，保留原记录、原因、经办人和复核人，生成差额与冲正。不能删旧票、改完数字后重新收费。
- 同一张票的同一明细只能确认一次费用基数；三套方案覆盖重叠时，不按三套分别抽成。
- 看板必须显示总成本、总奖金、服务费和净结果。命中率与盈利比例分别统计，零中奖、取消及未成交样本口径明确。

详细金额示例与收费未决项见[商业与金额规则](BUSINESS-RULES.md)。

## 全国门店带来的额外要求

全国推广前建立地区配置：省市、当地体彩机构、票型名称、终端支持范围、实际销售/兑奖安排、代销合同销售费用、依据文件与生效日期。不能把某省的“7%”、兑奖权限或截止时间复制成全国事实。

全国游戏基础规则统一核对，地方操作安排逐店确认。门店属于同一经营主体还是不同合作主体，需要在接入前明确；老板看哪些店、平台为何能处理客户数据，都需有授权依据。

税务判断不能仅看平台收集到的单张票；同一顾客可能在别店或本平台外有同一期奖金。ERP记录实际核实的兑奖和税款，不声称掌握全国完整中奖收入。[税务总局口径](https://fgk.chinatax.gov.cn/zcfgk/c100015/c5233844/content.html)

## 技术路线建议

先做能在手机和电脑使用的响应式网页，避免同时维护两套原生APP。手机重点是快速登记和拍照，电脑重点是核账与汇总；是否需要安装形态、离线能力或小程序，等试点证明需求再选。

初期采用一个后端服务、一套关系数据库和私有附件存储。把权限、规则计算、登记、结算、报表分成明确模块，暂不拆微服务。组织/门店权限在服务端校验，不能只隐藏前端按钮。计算与记账在可靠事务里完成；后台重试有防重复机制。

优先使用你已熟悉、能够维护的语言与框架。演练负载先采用南京3店、7天345笔模拟数据；实际规模、你熟悉的技术和预算仍待确定，因此不预定框架版本或云厂商。正式部署前需要确定运营主体、部署地区、适用备案与网络/数据保护要求、备份和恢复负责人；当前不承诺任何平台能直接上架。

## 从哪里开始

|阶段|要交付什么|进入下一步的依据|
|---|---|---|
|1 理解业务|完成第1、2课；与大哥及两位店长核对真实流程|你能独立判基本奖和算成本；说清登记发生在何时|
|2 准备样本|先用南京模拟数据与现有验收例题；真实试点前补脱敏真票、样账与合同信息|至少覆盖20个典型案例，不只选顺利和中奖案例|
|3 做流程原型|客户、登记、详情、核奖、日结五个主页面|店长用样本演练，指出漏项；先不导入真实批量客户|
|4 实现核心|权限、单式规则、登记、核奖、日结、导出|[验收案例](ACCEPTANCE.md)中适用项目通过|
|5 一店试点|连续7个营业日与原有账本并行核对|金额一致、没有重复结算与跨店泄露；计时确认省事|
|6 扩到少量店|新增任职、交班、地区配置和组织隔离验证|另一家店能独立使用，老板能追溯汇总明细|
|7 审查方案服务|政策与合同意见、服务范围、计算示例、责任人|确认可开展范围后再开发/启用实际收费与分成|

这些是依赖顺序，不是固定工期。学习、店长访谈与法规核实可以并行准备；核心登记功能可先规划，不能以技术验收代替经营许可。

试点目标建议：典型单式登记中位耗时不超过30秒；连续7天逐日账票核对一致；关键金额误差为0；重复入账为0；权限隔离无穿透；一次备份恢复成功。30秒是待店长验证的产品目标，不是现有性能。

## 现在需要补齐的资料

首批地区已定为江苏南京；模拟数量和登记记录已生成，见[南京首批模拟测试设定](NANJING-PILOT.md)。当前教学与原型不再等待真实门店清单。真实试点前再补已有账本、真实票型、店长交班方式、门店法律关系、代销合同销售费用、原票保管与兑奖责任；真样本需脱敏。
