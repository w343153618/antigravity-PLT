# 独立账号登录与权限隔离

2026-10-13，替代 Phase 3 的本地演示身份选择。领域范围仍以 CONTEXT.md 的事后对账约束为准。

## 账号与绑定

首次启动预置 `admin`（API 角色 `hq`）；已有店长时预置 `dianzhang`（`manager`），已有该店长名下客户时预置 `user`（`client`）。二者绑定同一门店的一位店长及其名下的一名客户，绑定 ID 写入 SQLite，重启不改变。初始口令为用户指定值，源码只保存独立盐的 scrypt 摘要，不在页面或文档显示明文。`AUTH_BOOTSTRAP_PASSWORD` 可覆盖尚未创建账号的初始口令，不能重置已有账号。既有 SQLite 账号中的大写角色继续兼容，所有登录、会话和 bootstrap API 返回小写角色。

空白库且 `DEMO_SEED=false` 时只有总部账号：不会虚构客户归属。初始化流程是总部建立首家门店和首位店长 → 重启以初始化店长账号 → 店长建立首个客户档案 → 重启以初始化客户账号；各次启动保持同一 AUTH_BOOTSTRAP_PASSWORD 配置。已有店长账号决定客户初始化归属，后续增加其他门店不会改变它。当前没有更多账号开通、重新绑定或密码重置页面。已有数据的自动绑定仅适用于本次三账号演示初始化；面向真实人员上线前需要明确账户归属并建立账号管理流程。

- `POST /api/auth/login`：仅接受 `{ username, password }`，返回该账号的角色与归属；传入 `role`、`clientId`、`managerId` 或 `subjectId` 等身份选择字段会拒绝。
- `GET /api/auth/me`：恢复当前会话。
- `POST /api/auth/logout`：撤销当前会话、清除 Cookie；重复退出安全。
- 原 `/api/demo/identities` 与 `/api/demo/session` 已移除。

会话使用随机 256 位令牌，浏览器 Cookie 具备 HttpOnly、SameSite=Strict、Path=/、8 小时有效期；服务端只存令牌摘要。重新登录撤销当前 Cookie 的旧会话。会话保存在单进程内存中，重启后重新登录；账号摘要、绑定及业务记录保存在 SQLite。不得把该模式扩展为多个无共享会话的应用实例。

本机 HTTP 开发默认不设置 Secure；HTTPS 访问时应配置 `COOKIE_SECURE=true`。反向代理须保留原始 Host（含非默认端口）。浏览器写请求的 Origin 须与当前应用的完整来源匹配，包括协议、主机和端口；Secure 模式按代理入口的 HTTPS 来源校验。不信任请求自行提供的转发头，也拒绝 Fetch Metadata 标记为跨站或同站不同来源的写请求。原生客户端未提供 Origin 时仍可正常使用；身份与归属权限照常检查。登录接口对来源 IP 和账号组合限速，超过限制返回 429 与 Retry-After。

## 权限矩阵

| 范围 | `client` | `manager` | `hq` |
|---|---|---|---|
| 本人历史存根与对账记录 | 只读 | 仅名下客户只读 | 全局只读 |
| 客户档案建档 | 禁止 | 当前店长直接或引荐建档 | 禁止 |
| 事后收支、存根登记 | 禁止 | 仅名下客户 | 禁止 |
| 凭证领取确认 | 禁止 | 仅名下客户且由本人登记的存根 | 禁止 |
| 门店、店长配置及既有策略/决议管理 | 禁止 | 禁止 | 允许 |
| 既有只读参考与核验日历 | 允许 | 禁止 | 允许 |
| 总部归属与对账审计 | 禁止 | 禁止 | 允许 |

匿名请求返回 401；登录后的角色越权、跨店或同店其他店长客户操作返回 403。输入错误返回 400，记录缺失返回 404，业务冲突返回 409。权限检查发生在业务请求解析之前，删除了旧内部免登录路径。权限表逐一匹配 HTTP 方法与注册路由，新增 API 未声明策略时默认拒绝，PATCH 不再笼统归给店长；HEAD 与对应 GET 使用同一权限策略。

`GET /api/bootstrap` 按当前会话裁剪资料：客户只收到本人档案、归属门店及店长，店长只收到本人、归属门店与名下客户，总部保留全局目录。店级客户、存根、账单、对账流水和汇总接口也按店长归属裁剪，同店其他店长资料不随响应发送。请求中的角色选择参数或自定义身份头不能改变账号绑定。`demo` 状态来自 SQLite 中的种子元数据，关闭 `DEMO_SEED` 或迁移已有合成库不会抹除演示标记。

页面根据登录账号渲染授权范围，不提供角色或档案选择器。退出及 401 会清空目录、表单、记录和对话框；迟到请求无法重新填入上一会话的数据。客户视图保持只读。

## Android

仓库 `android/app/src/main/java/cn/storeledger/customer/MainActivity.java`（原工作目录 `store-ledger/android/`）在 onCreate 的 super 调用后、内容渲染前设置 FLAG_SECURE。已完成 Java/DEX/APK 构建与签名验证；未完成真实设备截屏、录屏和多任务预览验证。平台能力边界参见 [Android 官方说明](https://developer.android.com/security/fraud-prevention/activities)，不声称可以抵抗所有设备、系统漏洞或外部拍摄。

现有 Android 客户端仍连接原 Python 门店账本后端；本次仅增加窗口安全标志，没有将它改接到 records-erp 的 Node 服务。Node 的三个预置账号用于新的网页工作台。

## 验证

新增 HTTP 测试覆盖默认拒绝匿名、小写账号角色绑定、拒绝身份字段、越权请求、跨店与同店不同店长的读写操作、目录与金额汇总隔离、新路由默认拒绝、HEAD 权限、伪造 Cookie、完整 Origin 和 Fetch Metadata 校验、退出/替换/过期会话、限速，以及 SQLite 重开后的绑定、口令与合成数据标记保留。旧 HTTP 回归改为先登录后执行；原业务断言保留，越权响应改为新契约的 403。

事后调账测试覆盖精确分单位增减、余额不足阻断、并发核减、同幂等键的重复请求和冲突请求。SQLite 故障注入验证：即使余额和流水已在内层事务写入，保存幂等收据失败仍回滚整笔操作；修复后同键重试可以完成一次登记。这些测试只验证线下实际收支的事后记录，不创建外部接口调用。

浏览器测试使用独立内存合成库和专用测试口令，没有修改实际数据。验收截图位于 `docs/qa/auth/`；历史 Phase 3 截图代表当时的演示身份版本。
